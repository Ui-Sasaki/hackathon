# FastAPIコーディング規約

## 1. 基本方針

- Python 3.11以上、FastAPI、Pydantic v2を使用する。
- APIは要件定義とIssueの完了条件を満たす最小単位で実装する。
- ユーザーID、権限、送信日時をクライアント入力から信用しない。
- 認証はSuperTokens、業務データはSupabase、業務ルールと認可はFastAPIが担当する。
- 公開APIの破壊的変更は、利用側と合意せずに行わない。

## 2. 配置

| パス | 責務 |
|---|---|
| `main.py` | `uvicorn main:app`用エントリーポイント |
| `app/main.py` | ASGIアプリの公開 |
| `app/cruds/main.py` | ASGIアプリ組み立て、ミドルウェア、開発用共有runtime |
| `app/api_support.py` | Repository依存関係、OpenAPI共通エラー契約 |
| `app/routers/main.py` | ヘルスチェックなどシステム系ルーター |
| `app/routers/*.py` | 機能領域別APIエンドポイント |
| `app/schemas/main.py` | Pydantic入出力スキーマ |
| `tests/main.py` | API・状態遷移・認可テスト |

現行構成を変更する場合は、同一Issue内で責務、import、README、テストをまとめて更新する。
機能追加時は既存の機能領域routerへ追加し、`app/cruds/main.py`へ業務endpointを戻さない。

## 3. 命名と型

- 関数・変数・モジュール内部値は`snake_case`を使う。
- クラスは`PascalCase`を使う。
- APIのJSONキーは既存仕様に合わせる。新規APIは原則`camelCase`へ統一する。
- 公開関数、依存関係、複雑な戻り値には型注釈を付ける。
- 状態や権限など有限集合は`Literal`またはEnumで制約する。
- `dict`を多用せず、外部との入出力にはPydanticモデルを定義する。

## 4. エンドポイント

- パスは複数形のリソース名を使う。例: `/requests/{request_id}`。
- HTTPメソッドとステータスコードを意味に合わせる。
- パスパラメータは`request_id`のようにリソース名を含める。
- 入力検証はPydanticの`Field`で長さ、範囲、形式を制約する。
- 一覧はカーソルページングを基本とし、取得上限を設定する。
- 更新系の重要操作は冪等性キーまたは楽観ロックを検討する。
- DB更新と関連状態の更新は、必要に応じてトランザクションまたはRPCで原子的に行う。

## 5. 認証と認可

- SuperTokensのセッション検証をFastAPI依存関係として提供する。
- Cookie認証ではHttpOnly、Secure、SameSiteとCSRF対策を有効にする。
- 認証後も所有者、ロール、利用停止、本人確認状態をAPIごとに検証する。
- `email_verified`と`verification_status`を別々に扱う。
- Service Role Key、セッション、アクセストークンをログやレスポンスへ出さない。
- Supabase RLSだけに依存せず、FastAPIでも業務上の認可を行う。

## 6. エラー

エラーは次の形式へ統一する。

```json
{
  "error": {
    "code": "REQUEST_STATE_CONFLICT",
    "message": "依頼の状態が更新されています",
    "details": {},
    "requestId": "trace_xxx"
  }
}
```

- 想定内の競合には409、認証失敗には401、権限不足には403を使う。
- 内部例外、SQL、個人情報をクライアントへ露出しない。
- エラーコードは機械判定可能な`UPPER_SNAKE_CASE`にする。

## 7. Supabaseアクセス

- DBアクセスをエンドポイント全体へ散らさず、CRUD関数へ閉じ込める。
- 検索条件はクエリビルダーのAPIを使い、文字列連結でSQLを組み立てない。
- 正確な緯度経度、本人確認画像などの機微情報を公開レスポンスへ含めない。
- 一意制約、外部キー、Check制約、RLSを前提にしつつ、APIで理解可能なエラーへ変換する。

## 8. 非同期処理

- 呼び出すSDKが非同期なら`async def`、同期なら`def`を使用する。
- `async def`内で同期I/Oを直接実行しない。
- 外部APIにはタイムアウトを設定し、再試行は安全な操作だけに限定する。
- バックグラウンド処理の失敗を握りつぶさず、ログと再実行方針を持つ。

## 9. テスト

- 正常系だけでなく401、403、404、409、422を対象にする。
- 状態遷移、所有者制約、重複操作、定員超過、冪等性を検証する。
- SuperTokensやSupabaseへの外部通信はテスト境界で差し替える。
- 各テストは順序に依存させず、データを初期化する。
- 実装完了後に関連テストを実行し、最後に全体テストを1回実行する。

## 10. 完了前チェック

- 要件とIssueの完了条件をすべて満たしたか。
- 認証・認可を画面側だけに任せていないか。
- 個人情報、秘密情報、正確な位置情報を漏らしていないか。
- OpenAPIとREADMEが実装に一致しているか。
- 変更に対応するテストがあり、全テストが成功するか。
