# 提出前チェックリスト

運営や審査者が公開URLを開いたときに、**新規登録とログインが動く**ことを保証するための手順である。
「ローカルでは動いた」は保証にならない。この文書の確認は**公開URLに対して**行う。

各項目はコマンドかブラウザ操作で結果を確認できる形にしてある。目視や記憶で済ませない。

## 1. 前提となる構成

このアプリの認証は3階建てで、どれか1つでも欠けると登録・ログインができない。

```
ブラウザ（審査者）
   ↓  EXPO_PUBLIC_API_URL
フロントエンド（Vercel）
   ↓  API_DOMAIN / WEBSITE_DOMAIN
バックエンド（FastAPI）
   ↓  SUPERTOKENS_CONNECTION_URI
SuperTokens Core
   ↓  DATABASE_URL
PostgreSQL（Supabase）
```

パスワードの保管とセッション発行は SuperTokens Core が行う。
**SuperTokens Core が無いと新規登録は原理的に成立しない**（`/auth/signup` が 404 になる）。

## 2. 最優先：静かに壊れる設定ミス

### 2.1 フロントエンドが `localhost` を向いていないか

`tetote/src/api/config.ts` は `EXPO_PUBLIC_API_URL` が未設定だと
`http://localhost:8000` にフォールバックする。この状態で公開すると、
フロントエンドは**審査者自身のPCの8000番**を叩きに行き、必ず接続拒否になる。

`EXPO_PUBLIC_*` は**ビルド時にコードへ埋め込まれる**。
Vercelの環境変数を後から変えても、**再ビルドしなければ反映されない**。

確認方法（公開URLをブラウザで開き、DevToolsのNetworkタブ）:

- [ ] 登録ボタンを押したときのリクエスト先が `localhost` **ではない**
- [ ] リクエスト先が本番APIのドメインになっている

### 2.2 認証モックが本番で有効になっていないか

`AUTH_MOCK_ENABLED=true` は**すべてのリクエストを認証済みとして通す**。
本番で有効だと、誰でも `usr_101` として全機能を操作できる。
現在の実装に `APP_ENV=production` での自動無効化は**入っていない**ため、
環境変数だけが安全装置である。

確認方法（Cookieを付けずにAPIを叩く）:

```bash
curl -i https://<本番API>/profile
```

- [ ] **401** が返る（200が返ったら認証が死んでいる。即座に `AUTH_MOCK_ENABLED` を外す）

### 2.3 モック初期化が本番で有効になっていないか

`MOCK_RESET_ENABLED=true` だと `POST /_mock/reset` が有効になり、
認証さえ通れば**全データを初期状態へ戻せる**。審査中に押されると発表内容が消える。

```bash
curl -i -X POST https://<本番API>/_mock/reset
```

- [ ] **404** が返る（200や401が返る場合は `MOCK_RESET_ENABLED` を外す）

## 3. 環境変数

### 3.1 フロントエンド（Vercel）

| 変数 | 設定値 | 備考 |
|---|---|---|
| `EXPO_PUBLIC_API_URL` | 本番APIのURL | **設定後に必ず再ビルド** |

- [ ] 設定した
- [ ] 設定してから再ビルドした
- [ ] Preview環境にも設定した（PRのプレビューを見せる場合）

### 3.2 バックエンド

| 変数 | 設定値 | 間違えたときの症状 |
|---|---|---|
| `SUPERTOKENS_CONNECTION_URI` | SuperTokens Coreの接続先 | 登録・ログインが5xx |
| `SUPERTOKENS_API_KEY` | Coreのキー | 同上 |
| `API_DOMAIN` | 本番APIのURL | Cookieが正しく発行されない |
| `WEBSITE_DOMAIN` | 本番フロントのURL | CORSで全リクエストが失敗 |
| `AUTH_COOKIE_SECURE` | `true` | HTTPSでCookieが拒否される |
| `AUTH_COOKIE_SAME_SITE` | `none` | **下記3.3を参照** |
| `APP_ENV` | `production` | Memoryへ落ちてデータが消える |
| `DATABASE_URL` | Supabaseの接続文字列 | 起動時に失敗する |
| `AUTH_MOCK_ENABLED` | **未設定または false** | 認証が無効化される |
| `MOCK_RESET_ENABLED` | **未設定または false** | 誰でもデータ初期化できる |

- [ ] すべて設定・確認した

### 3.3 Cookieの `SameSite`（最も気づきにくい壊れ方）

フロントエンドが `*.vercel.app`、バックエンドが別ドメインの場合、
ブラウザは**別サイト間の通信**として扱う。既定の `SameSite=lax` では
Cookieが送信されないため、次の症状になる。

> 登録もログインも成功したように見えるのに、画面がログイン状態にならない。
> リロードすると毎回ログイン画面へ戻る。

- [ ] `AUTH_COOKIE_SAME_SITE=none` と `AUTH_COOKIE_SECURE=true` を設定した
- [ ] 実際に登録 → **ページをリロード** → ログイン状態が保持されることを確認した

同じドメイン配下（例: `app.example.com` と `api.example.com`）に揃えられるなら、
その方が事故が少ない。

## 4. コールドスタート対策

無料枠のホスティングは、一定時間アクセスが無いとサーバーが停止する。
起動に30〜60秒かかることがあるが、`tetote/src/api/client.ts` の
タイムアウトは **10秒** である。

つまり**構成が正しくても、審査者の1回目のアクセスは失敗する可能性が高い**。

- [ ] 提出直前と、審査が始まる直前に公開URLを1度開いてサーバーを起こしておく
- [ ] 可能なら定期的にヘルスチェックを叩いてサーバーを起こし続ける
- [ ] 5分以上放置してから開き直し、1回目でも登録できることを確認した

## 5. 通し確認（公開URLで実施）

ローカルではなく**公開URLで、シークレットウィンドウ**で行う。
自分のブラウザには古いCookieが残っており、壊れていても動いて見えることがある。

- [ ] シークレットウィンドウで公開URLを開ける
- [ ] 新規登録できる
- [ ] 登録後にオンボーディングへ進める
- [ ] **リロードしてもログイン状態が保持される**
- [ ] ログアウトできる
- [ ] ログアウト後、同じアカウントでログインできる
- [ ] **別のシークレットウィンドウで別アカウントを登録すると、別ユーザーとして扱われる**
      （同じユーザーに見えるなら認証モックが有効になっている）
- [ ] スマートフォンの実機ブラウザでも登録できる（要件はスマホ優先）

## 6. 症状別の切り分け

| 症状 | 最も可能性が高い原因 | 確認方法 |
|---|---|---|
| 「通信に失敗しました」 | APIが起動していない／URLが `localhost` のまま／CORS | DevToolsのNetworkでリクエスト先とステータスを見る |
| 1回目だけ失敗し、2回目は成功する | コールドスタート | 5分放置して再現するか試す |
| 登録は成功するがログイン状態にならない | Cookieの `SameSite` | DevToolsのApplication→Cookiesに `sAccessToken` があるか |
| 登録時に500が返る | SuperTokens Coreへ繋がっていない | バックエンドのログを見る |
| `/auth/signup` が404 | `SUPERTOKENS_ENABLED=false` で起動している | バックエンドの環境変数を確認 |
| 誰でも同じユーザーになる | `AUTH_MOCK_ENABLED=true` | §2.2 の確認を行う |
| データが勝手に消える | Memory Repository／サーバー再起動 | `APP_ENV` と `DATABASE_URL` を確認 |

DevToolsのNetworkタブで**リクエスト先URLとステータスコード**を見るのが、
どの症状でも最初にやるべきことである。

## 8. 既知の弱点

提出時点で解消していない場合、提出物に明記しておくと誤解されにくい。

- `AUTH_MOCK_ENABLED` と `MOCK_RESET_ENABLED` に本番向けの自動無効化が無く、
  環境変数の設定漏れだけが安全装置になっている。
- `EXPO_PUBLIC_API_URL` 未設定時に `localhost` へ静かにフォールバックする。
  ビルドが成功してしまうため、設定漏れに気づけない。
- APIクライアントのタイムアウトが10秒で、コールドスタートに耐えられない。
- 画像とアプリ内データの一部はインメモリ保持のため、サーバー再起動で消える
  （`docs/image-upload.md`、`docs/cross-team-coordination.md` COORD-004 を参照）。
